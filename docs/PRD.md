## 1. 문제 정의

### 1.1 배경

카페 프랜차이즈 신규 알바 입사자는 보통 입사 후 1~2회 교육에서 메뉴와 레시피를 학습한다. 하지만 매머드 익스프레스 기준 음료 메뉴만 86종(디카페인 변형 미포함), 푸드·RTD·MD까지 합치면 150종을 상회한다. 짧은 교육 시간 안에 이를 모두 습득하기는 어렵고, 실전에서는 학습 부족이 곧 응대 실수와 손님 대기시간 증가로 이어진다.

기존의 학습 방식은 두 갈래다:

- **(a) 메뉴판 통째로 암기** — 비효율적이고, 카테고리·구조에 대한 이해 없이 단순 나열 암기로 끝남
- **(b) 유튜브 영상 시청** — 정보가 분산되어 있고, 검색·복습이 어려움

### 1.2 핵심 인사이트

매머드 음료 86종을 카테고리별로 분류해보면 **베이스 시럽·우유·차의 조합**이 반복 패턴으로 나타난다. 예컨대 커피 카테고리 20종 중 절반은 _헤이즐넛/꿀/바닐라/아몬드_ 4개의 베이스에 _커피 vs 라떼_ 변형이 붙은 구조다. 무작정 86개를 외우는 것보다, **데이터 구조 위에서 패턴을 학습**하는 편이 훨씬 효율적이다.

### 1.3 문제 진술

> 신규 알바 입사자가 짧은 교육 기간 동안 매머드 메뉴 체계를 효율적으로 습득할 수 있는 학습 도구가 없다.

## 2. 타겟 사용자

### 2.1 Primary User (현재)

**곽은서, 25세, 매머드 익스프레스 신규 입사자 (교육 D-7)**

- 카페 근무 경험 없음 (롯데리아 F&B 매장 경험 9개월은 있음)
- 컴퓨터공학 학사 + 데이터분석 부트캠프 수료
- 학습 시간: 교육일까지 약 7일, 일 1~2시간 가용
- 학습 환경: 데스크탑/모바일 혼용

### 2.2 Secondary User (확장 가정)

**매머드 익스프레스 전체 신규 입사자 (연간 추정 약 1,000명 단위)**

- 매머드 익스프레스 매장 수: 전국 약 900개 (출처: 매머드커피 공식)
- 가정: 매장당 연 평균 신규 알바 1~2명 → 연 약 1,000~1,800명 규모

**더 일반화하면**: 메뉴가 많은 프랜차이즈 카페·식음료 매장의 신규 근로자 일반

### 2.3 사용자 페인포인트

| 페인포인트                              | 현재 해결 방식             | 한계                   |
| --------------------------------------- | -------------------------- | ---------------------- |
| 메뉴 수 자체가 많음 (86+)               | 메뉴판 인쇄해서 암기       | 구조 없이 나열만 됨    |
| 비슷한 메뉴 헷갈림 (꿀 커피 vs 꿀 라떼) | 그때그때 물어보거나 외워둠 | 실전 응대 중 실수 발생 |
| 시즌 메뉴 업데이트                      | 매장에서 따로 안내받음     | 학습 자료에 반영 안 됨 |
| 디카페인 옵션 처리                      | 각각 별도로 외움           | 변형 패턴을 놓침       |

## 4. 기능 명세

### 4.1 핵심 기능 (MVP, v0.1)

#### F1. 메뉴 데이터베이스

- 매머드 익스프레스 전체 음료를 메뉴 단위로 그룹핑하여 JSON으로 보유 (139행 → 97개 메뉴)
- 메뉴 단위 필드: `name`, `cat`(카테고리), `is_new`, `is_discontinuing`, `variants`
- 각 메뉴는 `variants` 배열을 가짐 — 핫/아이스/ICE ONLY 등 온도 변형을 그룹 내에 포함
- variant 필드: `temp`(온도), `size`, `steps`(순서 있는 재료 배열), `note`, `uncertain`(불확실 플래그)
- 불확실한 재료는 `?` 표기로 보존 → 교육 시 확인 대상으로 활용
- v0.2 이후: `steps`를 객체로 확장 (그램수·동작·토핑 — 4.2 참조)

#### F2. 카테고리별 메뉴 브라우저

- 5개 카테고리(커피/콜드브루/논커피/티에이드/프라페블렌디드) + 전체 탭으로 분리, 각 탭에 메뉴 수 표시
- 카테고리 클릭 시 해당 메뉴 카드 리스트 표시
- 카드: 메뉴명 + 온도 옵션 배지 + 신메뉴/단종 플래그 + 레시피 입력 상태 + 카테고리 색상 블록(이미지 자리)
- 카드 클릭 → 상세 모달에서 온도(핫/아이스) 선택 → 사이즈 표시 → 선택한 변형의 제조 순서 표시
- 레시피 입력 진행률을 상단에 표시 (학습 동기부여)

#### F3. 메뉴 검색

- 한글/영문 어느 쪽이든 부분 일치 검색
- 결과 카드 형식으로 표시

#### F4. 퀴즈 모드

- **모드 A**: 한글명 → 카테고리 맞추기 (4지선다)
- **모드 B**: 영문명 → 한글명 맞추기 (4지선다)
- 결과 화면에 정답률/오답 노트 표시

#### F5. LLM Q&A

- Claude API 연동
- 메뉴 데이터를 시스템 프롬프트로 주입
- 자유 질문 가능 ("아메리카노랑 꿀 커피 차이가 뭐야?" 등)

### 4.2 향후 기능 (v0.2+)

#### 데이터 상세화 (레시피 업그레이드)

- 현재 step은 재료명 문자열 배열 (예: ["우유", "에스프레소 샷", "얼음"])
- 향후 step을 객체로 확장하여 다음 정보 추가:
  - `amount`: 그램수/용량 (예: "우유 150ml", "베이스 30g")
  - `action`: 동작 구분 (붓기 / 젓기 / 블렌더 / 토핑 / 드리즐 등)
  - `topping`: 토핑 단계 플래그 (휘핑크림·초코칩 등 마무리 토핑을 시각적으로 구분)
- **점진적 업그레이드 원칙**: 전체를 한 번에 바꾸지 않고, 그램수/동작이 실제로 중요한 메뉴부터 객체로 전환. 앱은 문자열 step과 객체 step을 모두 처리할 수 있도록 설계 (하위 호환).
- 블렌더·토핑 동작은 특히 프라페/블렌디드 카테고리에서 중요

#### 게임 모드 (타이쿤식 레시피 훈련) — 후순위

- 컨셉: 주문이 들어오면 제한시간 안에 재료를 올바른 순서로 골라 음료를 완성하는 게임 (쿠킹마마/오버쿡드 형식)
- 기존 `steps`(순서 있는 재료 배열) 데이터가 이 게임의 정답 시퀀스로 그대로 사용 가능 — 데이터 재활용
- 점수/콤보/제한시간 등 게임 요소로 반복 학습 유도
- 우선순위 낮음. 메뉴 학습 도구가 안정화된 후 별도로 구상

#### 기타

- 레시피 순서 맞추기 퀴즈
- 학습 진도 저장 (localStorage)
- 시즌 메뉴 업데이트 기능

### 4.3 명시적 제외 기능

- 사용자 인증/계정 — 1인용이므로 불필요
- 백엔드 서버 — 정적 호스팅으로 충분
- 모바일 앱 — 반응형 웹으로 대체
- 다국어 UI — 한국어 사용자만 대상

## 5. 기술 스택

| 분류       | 선택                                   | 선정 이유                        |
| ---------- | -------------------------------------- | -------------------------------- |
| 프론트엔드 | React + TypeScript                     | 작성자 기존 경험, 타입 안정성    |
| 스타일링   | Tailwind CSS                           | 빠른 프로토타이핑                |
| 상태관리   | React useState/useReducer              | 규모 작아 외부 라이브러리 불필요 |
| 데이터     | 정적 JSON 파일                         | DB 불필요, 빠른 로드             |
| LLM        | Anthropic Claude API (Claude Sonnet 4) | LLM Q&A 기능                     |
| 배포       | (미정 — Vercel 또는 GitHub Pages 후보) | 무료, 정적 호스팅                |
| 형상관리   | Git + GitHub                           | 포트폴리오 공개용                |

### 5.1 아키텍처 개요

```
[사용자]
   ↓
[React SPA (정적 호스팅)]
   ├── 메뉴 JSON 로드 (정적)
   ├── 카테고리/검색/퀴즈 (클라이언트 처리)
   └── LLM Q&A → Anthropic API 호출
```

백엔드 없음. API 키 노출 이슈는 학습 단계에서 임시 해결(.env 로컬만 사용) 후 v0.2에서 처리 고민.

면접관 후속 예상 질문:

- "데이터 구조는 어떻게 잡았어요?" → JSON 스키마 설명
- "왜 LLM Q&A를 붙였어요?" → 베이스 패턴 응용 질문(예: "꿀 들어간 메뉴 다 알려줘")에 대응하기 위해
- "지금 다시 만든다면 뭘 바꾸겠어요?" → API 키 관리, 학습 진도 저장, 시즌 메뉴 자동 업데이트
